# Findings

GraalVM CE 25.5.5 (`graal-25.5.5.0.3`), November 2026.

## Result

**GraalVM CE's released native-image builds working Windows on ARM64 executables**, with:

- four small patches to native-image (Java), applied with `-J--patch-module` — no GraalVM build;
- Substrate VM's C libraries (`libchelper.lib`, `jvm.lib`) compiled for ARM64 (one C patch);
- the JDK's static libraries built for ARM64 from labs-openjdk (`jvmci-25.5-b26`, `make static-libs-image`).

The [probe](probe/Hello.java) runs natively on a `windows-11-arm` runner and gives the same results as on x64:

## How

- **Build host**: the `windows-11-arm` runner. GraalVM CE **windows-x64** runs there under x64 emulation (native-image
  compiles its host JDK's classes, so the host must be Windows); MSVC's native ARM64 tools compile and run the C
  queries (`-H:+NewCAPCache`); `-Dsvm.platform=org.graalvm.nativeimage.Platform$WINDOWS_AARCH64` selects the target.
- **Output**: a relocatable object (`-H:+SharedLibrary -H:+ExitAfterRelocatableImageWrite`), linked by `link.exe`
  (ARM64), as graalvm-mobile does for iOS and Android.

## What was missing upstream, and the patches

Substrate VM already knows the platform (`Platform.WINDOWS_AARCH64`) and the AArch64 backend already follows the
Windows ABI (x18 reserved, variadic floats in integer registers). What it lacked:

| Where | Problem | Patch |
|---|---|---|
| `ErrHandlingAPI.CONTEXT` | x64 registers (`Rax`…`Rip`): the C queries fail with ARM64's `winnt.h` | [0002](patches/0002-windows-arm64-context.patch): ARM64's `CONTEXT` (`X[31]`, `Sp`, `Pc`, `Cpsr`) |
| `WindowsRegisterDumper` | reads R14/R15/RSP/RIP | [0002](patches/0002-windows-arm64-context.patch): X27 (heap base), X28 (thread), SP, PC |
| `PECoffMachine`, `PECoffHeaderStruct` | x64 only; the machine taken from `os.arch` (amd64 under emulation), the header hardcoding AMD64 | [0001](patches/0001-pecoff-arm64.patch): an `AARCH64` machine (0xAA64) taken from the target platform, its relocations (ADDR64, PAGEBASE_REL21, PAGEOFFSET_12A/12L, BRANCH19, REL32, SECREL, SECTION) |
| `PECoffUserDefinedSection.markRelocationSite` | writes the addend inline over the relocation site: over the instruction on ARM64 | [0001](patches/0001-pecoff-arm64.patch): the addend encoded in the instruction's immediate, where link.exe and lld-link read it |
| `WindowsUnwindInfoFeature` | emits x64 unwind codes for every Windows | [0004](patches/0004-unwind-info-amd64-only.patch): AMD64 only (see below) |
| `cpuid.c` (libchelper) | `_WIN64` taken for x86-64; MSVC defines no `__aarch64__` | [0003](patches/0003-libchelper-windows-arm64.patch): ARM64's CPU features from `IsProcessorFeaturePresent` |
| `ForeignFunctionsFeature` | Windows' foreign ABI is AMD64's | not patched: `-H:-ForeignAPISupport` (as graalvm-mobile on Android) |

`jvm.lib`'s `JvmFuncsFallbacks` (generated by mx) is regenerated as stubs from the windows-amd64 `jvm.lib`'s symbols.

## Not done / to check

- **ARM64 unwind info** (`.pdata`/`.xdata`): none for Java code yet. Faults are handled by a vectored handler, which
  needs none, but debuggers, ETW and crash dumps can't walk Java frames. ARM64's packed unwind data would do for most
  methods.
- **FFM** (`java.lang.foreign`) is off.
- **Bigger workloads**: graalvm-mobile's Lucene smoke test, then a Compose Desktop app (AWT: `awt.lib`, `jawt.lib` and
  `fontmanager.lib` are among the static libraries built).
- **`-march`**: the build falls back to `compatibility` (the emulated host doesn't report ARM64 features); fine for
  distribution, `armv8.1-a` could be set explicitly.
- **Debug info** (`-g`, CodeView): untested, its register mapping is x64's.
- **A kit and its release**, as graalvm-mobile's: the patch jars, `libchelper.lib`/`jvm.lib`, the JDK's static
  libraries and native-image's flags per GraalVM CE release, published by a daily workflow. The JDK's static libraries
  take ~1 h to build (once per labs-openjdk tag).
- **Upstream**: the patches are small and self-contained, candidates for oracle/graal.
